# Whiteboard-to-Workflow Handoff Template

Use this template when a solution whiteboard reaches `CONCLUDED`. The handoff
is the reviewed data contract between discovery and delivery routing. It is not
a second whiteboard, an implementation plan, or a runner-specific prompt.

Generate this document from the frozen whiteboard conclusion. Reference the
whiteboard for discussion history instead of copying the full conversation.
Replace all `<placeholders>` and remove instructional text from an instantiated
handoff.

## 1. Handoff control

| Field | Value |
| --- | --- |
| Delivery | `<short requirement/feature name>` |
| State | `DRAFT` |
| Source whiteboard | `<canonical link>` |
| Whiteboard state | `CONCLUDED` |
| Whiteboard conclusion version | `<commit/version/date>` |
| Target project/repository | `<canonical link/path>` |
| Governing project registry | `<link>` |
| Generated by | `<human/agent/automation identity>` |
| Fresh-context review | `<state + receipt or Not started>` |
| Human review owner | `<human>` |
| Review state | `NOT_STARTED` |
| Approved by | `Not approved` |
| Approved at | `Not approved` |
| Trigger mode | `<AUTOMATIC_ON_APPROVAL / MANUAL_INVOCATION>` |
| Workflow record | `Not generated` |
| Next action | `Submit handoff for review` |

The normalized conclusion is `IMMUTABLE_AFTER_APPROVAL`. Control and trigger
fields are `MUTABLE_CONTROL` only through `CONSUMED`; afterward they describe
the state at consumption and the generated workflow owns every live next
action. Do not keep advancing a consumed handoff as a second workflow ledger.

Lifecycle:

```text
DRAFT -> IN_REVIEW -> APPROVED -> CONSUMED
            |
            +-> CHANGES_REQUESTED -> DRAFT

material source-whiteboard change -> STALE -> regenerate and review
```

The handoff must not trigger routing merely because the file exists. Only an
explicit transition to `APPROVED` can trigger the workflow. The author first
self-reviews the exact candidate, then a newly created fresh-context agent
reviews it using the canonical
[review protocol](../reviews/fresh-context-agent-review.md). After fresh
approval, mandatory human review decides whether the design handoff becomes
`APPROVED`. Any candidate change invalidates both prior results and starts a new
self-review and fresh-review round. Neither agent may approve this design gate.

## 3. Handoff review gate

Review the handoff as one small artifact before routing. Confirm that it is a
faithful, complete, and unambiguous projection of the concluded whiteboard.
Before requesting review, complete the
[agent self-review](../reviews/agent-self-review.md) against the exact handoff
candidate and record `SELF_REVIEW_PASSED`. Any candidate change invalidates the
evidence and requires another self-review. Self-review is evidence, not
approval.

- [ ] The referenced whiteboard is `CONCLUDED` at the recorded version.
- [ ] Accepted requirements and solution match the frozen conclusion.
- [ ] Rejected discussion was not accidentally promoted into accepted input.
- [ ] Material boundaries, risks, policy gaps, and architecture decisions are
      present.
- [ ] Required evidence and deferred work are explicit.
- [ ] Project authorities and target repository are identifiable.
- [ ] No implementation detail was invented to fill a discovery gap.
- [ ] No secrets, private credentials, customer data, or transient signed URLs
      are included.

| Review round | Self-review evidence | Reviewer | Type | Result | Comments/link | Resolved in version |
| --- | --- | --- | --- | --- | --- | --- |
| `1` | `<SELF_REVIEW_PASSED record + candidate revision>` | `<identity>` | `<human/independent agent>` | `<APPROVED/CHANGES_REQUESTED>` | `<summary/link>` | `<version>` |

Approval statement:

`<Reviewer confirms that this handoff faithfully represents the concluded
whiteboard and is safe to use as delivery-workflow input.>`

## 4. Workflow trigger

When review changes the handoff to `APPROVED`, use one of these transports:

- `AUTOMATIC_ON_APPROVAL`: automation observes the approved version and starts
  the delivery router exactly once.
- `MANUAL_INVOCATION`: a human or agent explicitly starts the router, optionally
  with a case-specific prompt that references this approved handoff.

The transport may vary, but it must not redefine the handoff or workflow rules.
Record the consumed handoff version in the workflow. If the handoff later
becomes `STALE`, stop dependent generation and reroute from the new approved
version.

After the exactly-once trigger succeeds, change only the control/trigger record:
set the handoff state to `CONSUMED`, link the generated workflow, and set the
next action at consumption to manifest review. Preserve the approved normalized conclusion
unchanged so the workflow can identify the exact version it consumed.

| --- | --- |

| Trigger identity | `<automation/human/agent>` |
| Triggered at | `<date/timezone>` |
| Idempotency/run ID | `<value>` |
| Generated workflow | `<link>` |
